# Mirror Operator Collection Bundle Workflow

**Feature:** Run inside mirror operator collection bundle  
**Purpose:** Deploy the wizard on high-side (air-gapped) network with pre-loaded mirror registry configuration  
**Use Case:** Operations team mirrors OpenShift content on low-side, hands off bundle to high-side deployment engineers

---

## Overview

This workflow enables the wizard to run **inside** or **alongside** a mirror operator collection bundle on an air-gapped network. When the backend detects mounted mirror registry config files at startup, it pre-populates all mirror-related settings and locks them as read-only, allowing users to focus exclusively on:

- Cluster identity (name, domain)
- Networking configuration
- Platform-specific settings (vSphere, bare metal, etc.)
- Host inventory

**Key Benefit:** Eliminates duplicate mirror configuration work on high-side. The low-side mirror process produces config files that the wizard consumes directly.

---

## Two-Side Workflow

### Low-Side (Connected Network)

1. **Mirror OpenShift content** using Disconnected Mirror Operator or `oc-mirror`
2. **Generate mirror registry config** with credentials, CA cert, IDMS/ITMS files
3. **Bundle artifacts** into collection:
   - Mirror registry Quay deployment (or existing registry)
   - `imageset-config.yaml` - Defines mirrored OpenShift versions and operators
   - `idms-oc-mirror.yaml` - ImageDigestMirrorSet for digest-based mirrors
   - `itms-oc-mirror.yaml` - ImageTagMirrorSet for tag-based mirrors
   - `mirror-registry-config.json` - Registry hostname, port, credentials, CA cert path
   - `mirror-registry-ca.pem` - CA certificate for private registry
4. **Transfer bundle** to high-side network via approved transport (USB, one-way transfer, etc.)

### High-Side (Air-Gapped Network)

1. **Deploy mirror registry** (Quay or existing registry from bundle)
2. **Deploy wizard** with mounted config files via environment variables
3. **Wizard auto-loads** mirror settings at startup:
   - Pull secret generated from username/password
   - CA certificate loaded from file
   - Mirror sources extracted from IDMS/ITMS files
   - OpenShift version pre-selected from imageset-config.yaml
4. **User completes wizard** with cluster-specific settings:
   - Cluster name and base domain
   - Networking (IP ranges, VIPs, DNS, NTP)
   - Platform specifics (vSphere credentials, bare metal boot settings, etc.)
   - Host inventory
5. **Export install bundle** with all configs ready for deployment

## Environment Variables

The wizard detects mounted config files via these environment variables:

### Required for Mirror Registry Pre-Loading

**`MIRROR_REGISTRY_CONFIG`**  
Path to mirror registry configuration JSON file.

Example:
```bash
MIRROR_REGISTRY_CONFIG=/data/mirror-registry-config.json
```

### Optional for OpenShift Version Pre-Loading

**`IMAGESET_CONFIG`**  
Path to imageset-config.yaml from oc-mirror output.

Example:
```bash
IMAGESET_CONFIG=/data/imageset-config.yaml
```

## Configuration File Formats

### Mirror Registry Config (`mirror-registry-config.json`)

**Required fields:**
- `hostname` - Registry hostname (FQDN or IP)
- `port` - Registry port (e.g., 8443, 5000)
- `username` - Registry username
- `password` - Registry password

**Optional fields:**
- `caCertPath` - Path to CA certificate PEM file (for self-signed certs)
- `idmsPath` - Path to ImageDigestMirrorSet YAML file
- `itmsPath` - Path to ImageTagMirrorSet YAML file
- `email` - Email for pull secret (optional, defaults to empty)

**Example:**
```json
{
  "hostname": "registry.example.com",
  "port": 8443,
  "username": "admin",
  "password": "secret123",
  "caCertPath": "/data/mirror-registry-ca.pem",
  "idmsPath": "/data/idms-oc-mirror.yaml",
  "itmsPath": "/data/itms-oc-mirror.yaml"
}
```

**Security Note:** This file contains sensitive credentials. Ensure proper file permissions (0600 or 0644) and restrict access.

### ImageSet Config (`imageset-config.yaml`)

Generated by `oc-mirror` during mirroring process. Defines mirrored OpenShift versions and operators.

**Example:**
```yaml
kind: ImageSetConfiguration
apiVersion: mirror.openshift.io/v1alpha2
storageConfig:
  registry:
    imageURL: registry.example.com:8443/metadata
mirror:
  platform:
    channels:
      - name: stable-4.14
        type: ocp
        minVersion: 4.14.10
        maxVersion: 4.14.15
  operators:
    - catalog: registry.redhat.io/redhat/redhat-operator-index:v4.14
      packages:
        - name: advanced-cluster-management
        - name: cluster-logging
```

**What the wizard extracts:**
- `mirror.platform.channels[0].name` → OpenShift release channel
- `mirror.platform.channels[0].minVersion` → Pre-selected version
- Sets `blueprint.mirrorBundleDetected = true` flag

### IDMS File (`idms-oc-mirror.yaml`)

ImageDigestMirrorSet generated by `oc-mirror`. Maps upstream sources to mirror registry paths.

**Example:**
```yaml
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: oc-mirror
spec:
  imageDigestMirrors:
    - source: quay.io/openshift-release-dev/ocp-release
      mirrors:
        - registry.example.com:8443/openshift/release
    - source: quay.io/openshift-release-dev/ocp-v4.0-art-dev
      mirrors:
        - registry.example.com:8443/openshift/art-dev
```

**What the wizard extracts:**
- `spec.imageDigestMirrors[]` → Mirror sources for install-config.yaml `imageDigestSources` field

### ITMS File (`itms-oc-mirror.yaml`)

ImageTagMirrorSet generated by `oc-mirror`. Maps tag-based sources (operators, UBI images).

**Example:**
```yaml
apiVersion: config.openshift.io/v1
kind: ImageTagMirrorSet
metadata:
  name: oc-mirror
spec:
  imageTagMirrors:
    - source: registry.redhat.io/ubi9
      mirrors:
        - registry.example.com:8443/ubi9
    - source: registry.redhat.io/rhel9
      mirrors:
        - registry.example.com:8443/rhel9
```

**What the wizard extracts:**
- `spec.imageTagMirrors[]` → Mirror sources combined with IDMS sources

## Implementation Details

### Backend Startup Sequence

1. **Detect environment variables** (`MIRROR_REGISTRY_CONFIG`, `IMAGESET_CONFIG`)
2. **Load mirror registry config** (`mirrorRegistryConfigLoader.js`)
   - Validate required fields (hostname, port, username, password)
   - Generate pull secret from username:password (base64 encoded)
   - Load CA certificate from file (if caCertPath provided)
   - Parse IDMS/ITMS files for mirror sources
   - Return `{pullSecret, state}` object
3. **Load imageset config** (`imageSetConfigParser.js`)
   - Parse YAML to extract OpenShift version
   - Return state augmentation with version pre-selection
4. **Augment default state** (`index.js` defaultState function)
   - Merge mirror config into base state
   - Merge imageset config into base state
   - Store pull secret in memory-only variable (`mountedMirrorPullSecret`)
5. **Serve state** via GET `/api/state`
   - Inject `mountedMirrorPullSecret` before serving (ephemeral, never persisted)
6. **Generate YAML** via POST `/api/generate`
   - Inject `mountedMirrorPullSecret` before generation
   - Include pull secret in install-config.yaml if `includeCredentials: true`

## Security Considerations

### Credential Handling

**Pull secret is ephemeral:**
- Generated from username/password at startup
- Stored in memory-only variable (`mountedMirrorPullSecret`)
- Never persisted to SQLite database
- Injected into state only when serving GET `/api/state` or POST `/api/generate`
- Stripped by `getStateForPersistence()` before database writes

**Config file permissions:**
- Mirror registry config contains sensitive credentials
- Recommended permissions: `0600` (owner read/write only) or `0644` (owner read/write, group/others read)
- Backend runs as non-root user (UID 1000 in containers)
- Files must be readable by backend process user

**CA certificate handling:**
- Loaded from file at startup
- Stored in state (safe, non-sensitive)
- Included in exported bundles (necessary for install)

### File Access Validation

Backend validates all file paths before reading:
- Config file must exist and be readable
- CA cert file missing logs warning but proceeds (registry might use system root CAs)
- IDMS/ITMS files missing logs warning and uses default mirror sources
- Invalid JSON/YAML logs warning and returns null (graceful degradation)

### Network Isolation

In air-gapped deployments:
- Backend has no outbound internet access
- Cincinnati version discovery disabled (uses pre-selected version)
- Operator catalog sync disabled (operators defined in imageset-config.yaml)
- Pull secrets only work with configured mirror registry

## Troubleshooting

### Config Not Loading

**Symptom:** Mirror fields not locked, no pre-configuration  
**Cause:** Environment variable not set or file not found

**Check:**
```bash
# Inside container
echo $MIRROR_REGISTRY_CONFIG
ls -la $MIRROR_REGISTRY_CONFIG

# Check backend logs
grep "Mirror registry config" /path/to/backend.log
```

**Expected log:**
```json
{"tag":"startup","registryFqdn":"registry.example.com:8443","username":"admin","hasCaCert":true,"sourcesCount":4,"sourcesFrom":"IDMS/ITMS","msg":"Mirror registry config loaded successfully"}
```

### Permission Denied Reading Config File

**Symptom:** `EACCES: permission denied` error in logs  
**Cause:** Config file permissions too restrictive, backend runs as non-root

**Fix:**
```bash
# Allow backend user (UID 1000) to read file
chmod 644 /path/to/mirror-registry-config.json
chown 1000:1000 /path/to/mirror-registry-config.json

# OR in Kubernetes, set proper SecurityContext
securityContext:
  runAsUser: 1000
  fsGroup: 1000
```

### Pull Secret Not Appearing in install-config.yaml

**Symptom:** install-config.yaml shows `__PULL_SECRET_PLACEHOLDER__`  
**Cause:** Export option "Include credentials in export" not checked

**Fix:**
1. Go to Assets & Guide step
2. Scroll to Export Options section
3. Check ☑️ "Include credentials in export"
4. Pull secret now appears in preview

### CA Certificate Not Loading

**Symptom:** `mirrorRegistryUsesPrivateCa: false` despite caCertPath set  
**Cause:** CA cert file not found at specified path

**Check:**
```bash
# Verify CA cert file exists and is readable
ls -la /path/to/ca.pem
cat /path/to/ca.pem | head -1
# Should show: -----BEGIN CERTIFICATE-----
```

**Expected log:**
```json
{"tag":"startup","caCertPath":"/data/mirror-registry-ca.pem","bytes":1500,"msg":"Loaded mirror registry CA certificate"}
```

### IDMS/ITMS Not Loading

**Symptom:** `sourcesFrom":"defaults"` in logs instead of `"IDMS/ITMS"`  
**Cause:** IDMS/ITMS files not found or invalid YAML

**Check:**
```bash
# Verify files exist
ls -la /path/to/idms-oc-mirror.yaml
ls -la /path/to/itms-oc-mirror.yaml

# Validate YAML syntax
cat /path/to/idms-oc-mirror.yaml | grep -A 5 "kind:"
# Should show: kind: ImageDigestMirrorSet
```

**Expected logs:**
```json
{"tag":"startup","filePath":"/data/idms-oc-mirror.yaml","count":2,"msg":"Parsed IDMS file successfully"}
{"tag":"startup","filePath":"/data/itms-oc-mirror.yaml","count":2,"msg":"Parsed ITMS file successfully"}
{"tag":"startup","idmsCount":2,"itmsCount":2,"total":4,"msg":"Loaded mirror sources from IDMS/ITMS files"}
```

### ImageSet Config Not Pre-Selecting Version

**Symptom:** Blueprint step shows no pre-configured badge  
**Cause:** IMAGESET_CONFIG env var not set or file invalid

**Check:**
```bash
echo $IMAGESET_CONFIG
ls -la $IMAGESET_CONFIG
cat $IMAGESET_CONFIG | grep -A 5 "channels:"
```

**Expected log:**
```json
{"tag":"startup","configPath":"/data/imageset-config.yaml","channelName":"stable-4.14","version":"4.14.10","channelCount":1,"msg":"ImageSet config loaded successfully"}
```

## FAQ

**Q: Can I change the pre-loaded OpenShift version?**  
A: Yes, the version field remains editable. The pre-selected version matches the mirrored content, but you can select a different version if the imageset-config contains multiple versions.

**Q: What happens if I don't provide IDMS/ITMS files?**  
A: The wizard uses default mirror sources with your registry FQDN:
- `quay.io/openshift-release-dev/ocp-release` → `your-registry:port/ocp-release`
- `quay.io/openshift-release-dev/ocp-v4.0-art-dev` → `your-registry:port/ocp-v4.0-art-dev`

**Q: Can I use this with an unauthenticated mirror registry?**  
A: Yes, but you still need to provide a username/password in the config file. The wizard generates a pull secret from these credentials. For truly anonymous registries, use the regular wizard flow without mounted configs.

**Q: Does the pull secret get persisted to the database?**  
A: No. The pull secret is held in memory only (`mountedMirrorPullSecret` variable) and never written to SQLite. It's injected into state when serving API requests but stripped before database writes.

**Q: Can I import a state file that was exported with pre-loaded config?**  
A: Yes. When you import a state file, the pull secret and CA cert are excluded (for security). The wizard shows a post-import warning banner listing all credentials you need to re-enter. On the high-side, you would mount the config files again to restore the pre-loaded settings.

**Q: What if my mirror registry uses system root CAs (not self-signed)?**  
A: Omit the `caCertPath` field from the config JSON. The wizard sets `mirrorRegistryUsesPrivateCa: false` and doesn't include a CA certificate in the trust bundle.
