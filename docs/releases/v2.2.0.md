# OpenShift Airgap Architect v2.2.0

**Version:** 2.2.0 (MINOR — new feature) · **Supported OpenShift targets:** 4.20, 4.21, 4.22 (unchanged) ·
**Release evidence:** see [SBOM and provenance](../security/SBOM_AND_PROVENANCE.md) · **Published assets, if any:** the
[Releases page](https://github.com/bstrauss84/openshift-airgap-architect/releases)

v2.2.0 adds a second workflow beside Install: **Mirroring**. It plans and runs oc-mirror v2 without an install.
You can mirror the OpenShift platform release, operators and additional images in independent profiles. Content
can go to disk and across the air gap with a verified transfer, or straight into your registry. v2.2.0 also carries
a few Install corrections. It is a minor feature release on top of [v2.1.2](v2.1.2.md). OpenShift support is
unchanged, and so is the deployment model:

```bash
podman compose up --build -d
# or
docker compose up --build -d
```

Before updating, save your configuration with **Tools → Export Run**, and follow [`docs/UPDATING.md`](../UPDATING.md).
Mirroring profiles are kept on the server and are **not** part of an exported run.

---

## What this release is about

**Mirroring, as its own workflow.**
- **Where:** the landing page now offers **Mirroring** beside Install. Upgrade is still "coming soon".
- **What a profile is:** a Mirroring profile is one set of content you want to mirror. It has its own OpenShift
  release, its own storage and its own history, and it is separate from the Install workflow.
- **Separation from Install:** nothing in Mirroring changes Install. Install's Start Over, Export Run and Import Run
  leave Mirroring profiles alone.

The full guide is [Mirroring workflow — user guide](../MIRRORING_WORKFLOW.md#part-a--user-guide). The README's
[Mirroring workflow](../../README.md#mirroring-workflow) section has a quick start.

| 4.22 | Supported |
| 4.23 and later | Not supported — rejected deterministically |

The same versions apply to Install and Mirroring.
- **Mirroring checks:** a profile's platform release minor, its patch's minor and its operator catalog minor are each
  checked when you save, preview, run preflight and run.
- **Unsupported versions:** an unsupported version is refused (HTTP 422), never replaced by a supported one.
- **Additional images:** a profile with only additional images needs no OpenShift version.

## Added — Mirroring

### Profiles and content
- **Profiles** — create, rename, change content and delete. Deleting removes the record, never data on disk. Each
  profile has a status in words and a list of anything still to fix, each with a **Go to** button. Content tabs:
  **Platform**, **Operators**, **Additional images**, plus **Run & transfers**.
- **OpenShift platform** — the same release selector as Install (channel and patch), per profile. **Lock release**
  holds the release steady while you build the rest of the profile. Each profile has its own lock, separate from
  Install's.
- **Operators**:
  - **Scan catalogs** — downloads the Red Hat, Certified and Community catalogs for one OpenShift minor and lists
    them. It needs a Red Hat pull secret, and the listing is kept on the server.
  - **Catalogs follow the release** — with platform content, the catalogs follow the platform's minor.
  - **Choosing operators** — add operators from the catalog browser, which has search, or apply the **Scenario Quick
    Picks** shared with Install. A pick adds only operators the scanned catalogs contain.
  - **Check catalogs** — asks the live catalogs whether each selected package, channel and version range exists
    today. Packages that are not found, or a channel that does not exist, block the run. Anything that could not be
    checked is reported as not verified.
- **Additional images** — any image references, one per row or several at once (**Add several…** also reads an
  ImageSetConfiguration's `additionalImages`).
- **Import YAML** — reads existing ImageSetConfiguration files into profiles. Validation is bounded and strict.
  Invalid files are never applied. Parts the editor cannot represent become explicit review items, and the original
  file is kept unchanged with the profile.

### ImageSetConfiguration
- **Show YAML** shows the profile's ImageSetConfiguration. While the profile still has items to fix, it shows a
  labelled **DRAFT** that cannot be downloaded. Once the profile is ready, it shows the validated file.
- Install and Mirroring share one structural check against the oc-mirror v2 ImageSetConfiguration schema. Where
  Architect is stricter than oc-mirror, the finding says so.

### Three workflows
| Workflow | Where it runs | What it does |
|---|---|---|
| **Mirror to disk** → **Prepare transfer** | Connected side | Downloads the images into archive files, then adds checksums (`SHA256SUMS`), the exact configuration and its provenance (`oaa-transfer/`) |
| **Receive transfer** → **Disk to mirror** | Disconnected side | Verifies every copied file, then uploads the archives into your registry with the received configuration, byte for byte |
| **Mirror to mirror** | One machine that reaches both sides | Copies straight from the sources into your registry |

- **Preflight** checks the following before each run, and nothing runs while an item blocks:
  - paths, free space and write access
  - credentials and the destination
  - the configuration and run options
  - the oc-mirror binary (version, commit, SHA-256)
  - registry trust and profile isolation
  - existing archives and the live catalog check
  - for disk to mirror: the received configuration's identity and the transfer order
- **One oc-mirror run at a time** on a server, across Install and Mirroring.
- **Immutable plans** — every run first writes a read-only plan: the exact configuration given to oc-mirror, its
  SHA-256, the oc-mirror binary and the options.
- **Storage location** — each profile uses any directory the server can write, typed or picked with **Browse…**. It
  is chosen while the profile has written nothing. `OAA_MIRROR_STORAGE_ROOT` sets the default for new profiles.
- **Run options** — parallel images and layers, retries, timeouts, log level, archive size and `--since` for mirror to
  disk. They are saved per profile and checked the way oc-mirror checks them.

### Transfer and integrity
- **Prepare transfer** works on a completed mirror to disk:
  - **What it checks** — it hashes every archive, checks the archived image blobs against their digests, and records
    which catalogs oc-mirror pinned to a digest.
  - **What it writes** — `SHA256SUMS` and `oaa-transfer/` (`transfer-manifest.json`, the exact `imageset-config.yaml`
    and `plan.json`, and `README-TRANSFER.txt`).
  - **Credentials** — none are written.
  - **Unpinned catalogs** — a catalog left as a tag marks the transfer as not ready for offline use. Prepare stops
    unless you confirm, and every later step says so.
- **Receive transfer**:
  - **Checks before copying** — it re-hashes every file against the manifest before copying anything. Each problem is
    named with a recovery step: missing, altered, a short copy, an extra archive, unsafe names or tar entries, or an
    unsupported OpenShift version.
  - **Where it goes** — the transfer goes into the profile it came from when the server has it. Otherwise it goes into
    a read-only **Received** profile.
- **Transfer order** — each mirror to disk records whether it is a full or a delta cycle and which cycle it follows.
  The disconnected side refuses two cases before oc-mirror runs:
  - a delta whose predecessor was never loaded;
  - anything older than what was already loaded.

  **Full transfer** is the explicit repair for a gap.
- **Archives are kept** — each successful mirror to disk's archives move into a set of their own. A later run, a dry
  run or a failed run therefore never deletes an unprepared transfer.
- **Disk to mirror network confinement** — on by default. oc-mirror can reach only the destination registry, so a
  transfer that is not complete for offline use fails instead of quietly reaching the internet.
- **oc-mirror build check** — on receipt, and in the disk-to-mirror preflight, the disconnected side compares its own
  oc-mirror executable with the SHA-256 recorded in the transfer. The results are same bytes, different bytes or not
  recorded. The check never blocks and downloads nothing. "Same bytes" proves identical bytes only; it is not a FIPS or
  suitability statement. `README-TRANSFER.txt` explains how to check by hand, offline. Transfers do not include
  oc-mirror or oc in v2.2.0.

### Credentials
- **Red Hat pull secret (source):**
  - **How you give it** — paste, drag and drop, upload, or switch on **Use the pull secret mounted into the
    container**. The mounted secret is never used unless you switch it on.
  - **How long it is kept** — a pasted secret stays in page memory for one profile. You enter it once and confirm it
    with **Use it here** elsewhere. It is gone after a reload, Forget, or profile deletion.
- **Destination registry:**
  - **What you enter** — a destination (`host[:port][/path]`) and an auth file per run. **Help me generate** builds the
    auth file in the browser.
  - **Anonymous access** — this option sends the placeholder credential that OKD documents for registries without
    authentication.
- **No credential is ever stored.** None is saved in the profile, server state, browser storage, plans, transfers or
  logs.
- **Which credentials each workflow sends** — mirror to disk sends only source credentials, and disk to mirror only
  destination credentials.
- **Auth files** — temporary auth files live in a private memory-backed directory.

### Operations
- **What it lists** — the Mirroring **Operations** view lists every run, transfer, receipt and catalog check, plus the
  catalog scans started from a profile.
- **What a selected entry shows:**
  - the outcome
  - the oc-mirror build, plan and configuration checksums
  - the archive files with their sizes and SHA-256
  - the command, with the credentials file hidden
  - related operations
  - the stored log, with credentials removed
- **Run the same again** — offered for runs that stopped for a temporary reason. It repeats the original plan exactly,
  with fresh credentials, and checks the result before reporting it. For operator and additional-image failures that
  fail only on a signature read, the retry is scoped to the affected repositories.

## Changed

- **Landing page and recovery.** Mirroring sits on the landing page. If an Install run uses an unsupported OpenShift
  minor, its recovery screen also offers **Open Mirroring**.
- **Shared Tools drawer.** Install and Mirroring open the same Tools drawer, with **Home**, theme, and (Install only)
  Export/Import Run and Start Over. **Home** never resets anything.
- **Field Manual FIPS checklist.** For FIPS-enabled configurations, the Field Manual now points to the FIPS-capable
  installation program Red Hat documents (`openshift-install-fips`). It no longer claims that oc-mirror builds are
  FIPS-capable, because Red Hat makes no FIPS statement for oc-mirror. Only that sentence changes.
- **Generated SSH keys** carry the neutral comment `openshift-airgap-architect-generated`. Previously they carried the
  server's `user@hostname`, which was a workstation account and domain, or a container's user and ID. Keys you paste
  keep their own comment.

## Fixed (Install and shared)

1. **Run oc-mirror (Install):**
   - **Cache directory** — the cache directory is used for all three workflows. Mirror to mirror previously wrote to an
     unshared cache in the container's home directory.
   - **`--since`** — it is passed only for mirror to disk, and the hint states the only accepted format,
     `yyyy-MM-dd`.
   - **External ImageSetConfiguration files** — they are now accepted by preflight. Previously every external file was
     blocked.
   - **Parallel images and layers** — limited to 1–10, the binary's own limits.
2. **Archive size** must be a whole number of GiB (at least 1). Fractions and negatives were accepted, and oc-mirror
   refuses them. Valid inputs produce identical output.
3. **Locking the Install release** saves any pending selection first. An incomplete release selection is refused
   instead of being locked.
4. **Install Start Over** no longer cancels Mirroring runs or touches Mirroring profiles.
5. **Trust & Proxy:**
   - **Before** — the HTTP Proxy, HTTPS Proxy and No Proxy fields scrolled sideways at most window widths, and two of
     them sat partly off the sides.
   - **Now** — they share the row and stack on narrow screens. They resize vertically only.
6. **Tall dialogs** scroll inside themselves.

## Deployment

- **Optional Mirroring storage volume.** `docker-compose.yml` documents mounting a host directory and setting
  `OAA_MIRROR_STORAGE_ROOT`, so large Mirroring content can live on its own volume.
- **Enterprise hosts.** [`docs/ENTERPRISE_PODMAN_DEPLOYMENT.md`](../ENTERPRISE_PODMAN_DEPLOYMENT.md) covers RHEL 9 with
  Podman 4.9, FIPS and an HTTPS-inspecting proxy. `scripts/deploy/oaa-deploy.sh` provides staged `preflight`, `build`,
  `up` and `verify` steps, and it never starts a stale image after a failed build.
- **Corporate CA at build time.** An optional `oaa_build_ca` build secret supplies a corporate CA for package and tool
  downloads during the image build. It is not stored in the image. Tool-download failures now say whether TLS, the
  proxy or the HTTP response was the cause.
- **Disconnected side.** The runtime package sets `AIRGAP_RUNTIME_SIDE=high-side`. With it, the backend skips the
  update-service warm-up and the update check.
- The container base images are unchanged.

## Security

- **Backend dependency updates:** `undici` 7.30.1, `zod` 4 (from 3) and `body-parser` 1.20.9 (as an override). These
  address published advisories in those packages.
- **Catalog downloads verify TLS.** Scans and catalog checks fetch catalog images themselves and verify TLS against the
  same trust oc-mirror uses (`SSL_CERT_FILE`, `SSL_CERT_DIR`, `/etc/containers/certs.d`).
  - **Integrity** — every manifest and blob is checked against its digest.
  - **Credentials** — they are sent only to the HTTPS endpoints the registry names, never across a redirect.
  - **On failure** — a certificate that cannot be verified stops the scan before any request is sent.
- **Mirroring credentials are never persisted** (see *Credentials* above). API responses are `no-store`.
- **No real host identity in generated SSH keys** (see *Changed*).

## Testing and certification

- **What was run on this source:**
  - the full frontend, backend and tooling suites;
  - the version, documentation and secret-scanning gates;
  - the production build;
  - the Install golden-output comparison (all 924 generated files);
  - real-browser checks of Mirroring and the changed Install screens against isolated instances.
- **Exact-binary lab tests.** The three Mirroring workflows were run with the real oc-mirror 4.22.19 binary against
  **synthetic** registries, in network-isolated lab environments:
  - mirror to disk → Prepare transfer → carry → Receive transfer → disk to mirror;
  - mirror to mirror;
  - transfer order, rollback refusal, damaged and incomplete transfers;
  - the oc-mirror build check (same and different builds).

  The disconnected side made no outside connections. Catalog scans were also run against the real Red Hat 4.22
  catalogs (listing only).
- **Not exercised:** see *Known limitations*. In particular, no OpenShift release payload and no real Red Hat operator
  images have been mirrored end to end.
- **Certification.** This document deliberately states **no** certification verdict for v2.2.0. A verdict is valid
  only for a run bound to the exact released commit. It is published with that release's evidence on the
  [Releases page](https://github.com/bstrauss84/openshift-airgap-architect/releases), together with any owner risk
  acceptance. Certification evidence, verdicts and owner acceptance for earlier releases are bound to their own
  commits and **do not carry over**.
- **Earlier findings still apply.** The base images are unchanged, so the image-vulnerability findings reported for
  earlier releases are **not** resolved by this release. See [SBOM and provenance](../security/SBOM_AND_PROVENANCE.md).

## Known limitations

- **Not yet demonstrated end to end:**
  - mirroring an OpenShift platform release payload into a real disconnected registry;
  - transferring real Red Hat operator content;
  - Quay or other production registries as the destination;
  - a customer RHEL 9 / Podman 4.9.4 / FIPS host with a corporate proxy CA.

  The lab tests above used synthetic content.
- **oc-mirror and FIPS.** Red Hat publishes no separate FIPS oc-mirror build and makes no FIPS statement for oc-mirror.
  Architect makes none either. Install the oc-mirror build for the RHEL version you use.
- **Tools are not carried in a transfer.** Bring oc-mirror (and oc) to the disconnected side yourself; the build check
  tells you whether it is the same executable.
- **Signatures through an archive.** Disk to mirror does not carry sigstore signatures through the archive, and
  signature retries are not offered for disk to mirror.
- **Upstream oc-mirror limitation.** oc-mirror cannot mirror a digest-referenced additional image from a registry
  address that includes a port.
- **Result checks** read the archive and oc-mirror's own records, not the source registries. Exit code 0 is reported
  as oc-mirror's own claim. Checking the destination needs it to be reachable with the run's credentials.
- **Catalog checks list default channels only.** The scanned catalogs list default channels. A non-default channel
  from an imported file is confirmed only by **Check catalogs**.
- **Upgrade is still "coming soon"** on the landing page.

## Post-publication known issue (2026-11-06)

*Added after publication. Not part of the signed release record; the tag `v2.2.0` and the release assets are unchanged.*

**Mirroring runs fail in the v2.2.0 backend container.**

- **Symptom:** every Mirroring run (mirror to disk, mirror to mirror, disk to mirror) stops before `oc-mirror` starts, with
  `The execution plan could not be written, so nothing was run: EACCES: permission denied, open '/usr/local/bin/oc-mirror'`.
- **Cause:** `backend/Containerfile` extracts Red Hat's `oc-mirror` with the tarball's owner (uid 984) and adds `+x`, giving mode
  `0751`. The backend runs as `appuser` (uid 1001), which can execute the binary but cannot read it. The run plan records the
  binary's SHA-256, so the read fails.
- **Reproduced** on the certified backend image (config `sha256:839d6523b04d…`) as uid 1001: `sha256sum /usr/local/bin/oc-mirror`
  reports "Permission denied". A mirror-to-disk run through the API fails as above.
- **Why testing missed it:** the lab tests ran the backend on the host with a configured `oc-mirror`, not the container's own
  binary and user.
- **Not affected:** Install, operator catalog scans and the other workflows.
- **Recommendation:** do not rely on v2.2.0 for Mirroring runs. The correction is planned for v2.2.1. v2.2.0 is not changed.
