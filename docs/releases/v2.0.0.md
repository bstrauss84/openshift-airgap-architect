## What this release is about

v1.x generated OpenShift configuration for essentially one OpenShift version. The
parameter lists, help text, documentation links and validation rules were written for a
single release, and nothing in the app knew which OpenShift version you were targeting.

That worked until it didn't. Fields come and go between OpenShift releases, defaults
change, and documentation URLs move. An app that cannot tell 4.20 from 4.21 will quietly
offer you a field that does not exist in your release, or link you to documentation for
the wrong one.

**v2.0.0 rebuilds the application around the OpenShift version you select.** You choose
a version, lock it, and from that point the parameter catalog, the UI fields, the
validation rules, the Field Guide and every documentation link follow that choice. If
you pick a version the app does not support, it stops and tells you — it never guesses.

## Supported OpenShift versions

| Version | Status |
|---|---|
| 4.20 | Supported (baseline) |
| 4.21 | Supported |
| 4.22 and later | **Not supported** — rejected deterministically |

Availability of a release in Cincinnati is not the same as support in this tool.
Supporting a version means the app carries an audited parameter catalog, Field Guide
content, validation rules and a generation contract for it.

## Added

### Version awareness, end to end

- **Version selection and locking.** You choose an OpenShift minor version and a patch
  release, then lock it. Locking is what allows every later step to rely on a single
  known target. You can unlock and change it later.
- **Per-version parameter catalogs.** Each supported version has its own audited list of
  install-config and agent-config parameters, with which fields exist, what values they
  accept, and which Red Hat documentation describes them.
- **Version-gated fields.** Fields appear only on the versions that actually have them.
  A field introduced in 4.21 is simply not present when you are targeting 4.20.
- **"New in 4.21" annotations.** Fields introduced since the baseline are marked, so you
  can see at a glance what is new to you.
- **Deprecation annotations** for vSphere legacy placement fields.
- **Version-correct documentation links** everywhere, including in the Field Guide.

### New OpenShift 4.21 parameters

- AWS EBS root volume throughput, for both control-plane and compute machines
- AWS Confidential Compute (AMD SEV-SNP)
- Azure shared-key access control (`allowSharedKeyAccess`)
- Azure bring-your-own VNet with named subnets and role assignment
- Bare-metal BMC CA certificate verification (`bmcVerifyCA`)

### Saved configurations and exports

- **New saved-configuration format (schema v3)** with the OpenShift version as a
  first-class, locked property. Configurations saved by v1.x are migrated automatically
  when you open or import them.
- **Version manifest in exported bundles** (`version-manifest.json`) recording the exact
  OpenShift minor and patch the bundle was generated for, plus checksums for the files
  it contains.
- **Bundle validation**, so you can check an exported archive is intact and internally
  consistent before relying on it.

### Field Guide

- Version-specific content, selected strictly by the version you locked.
- **Fails closed:** if the Field Guide cannot establish exactly which version you mean,
  it refuses to produce a document rather than guessing. A guide that confidently
  describes the wrong release is worse than no guide.
- Provenance certification ensuring every section and documentation link belongs to the
  version being described.
- Corrected platform prerequisites, AWS AMI lookup guidance, and bare-metal provisioner
  guidance.

### vSphere

- Full inventory-path support for failure-domain topology fields (compute cluster,
  datastore).
- Automatic conversion from the legacy path style to failure-domain paths during
  generation.
- UI placeholders and hints updated to show the correct path format.

### Testing

- A comprehensive Playwright end-to-end suite (405 tests at the time it was added),
  covering the wizard flows, per-step behaviour and generated-asset structure.
- Substantially expanded backend and frontend coverage, including enforced HTTP
  boundaries for unsupported versions.

## Changed

- **An OpenShift version lock is now required before generating.** This is the central
  behavioural change of the release: the locked version determines the parameter
  catalog, the Field Guide content and the validation rules.
- **Unsupported versions are rejected, not approximated.** Selecting an unsupported
  version produces a clear recovery screen with a button to switch to a supported one.
  Nothing downgrades silently.
- User-facing text is version-neutral where it should be, and version-specific where it
  must be, with an automated check that keeps it that way.
- Operator catalog handling follows the selected version, so the operator index you
  mirror matches the cluster you are building.
- Mirroring documentation references were made neutral rather than tied to one release.

## Fixed

- Canonical version state handling in the backend, so the version you chose is the
  version every later step sees.
- Unsupported-version HTTP boundaries, which previously were not consistently enforced
  across all endpoints.
- Unsupported-version recovery screen styling.
- vSphere legacy mode now builds full inventory paths for compute cluster and datastore
  instead of partial ones.
- vSphere failure-domain placeholders corrected to show full inventory paths.
- Frontend shared-module resolution in container builds.
- Host-inventory editing and comma-separated list behaviour.
- Field help popovers no longer render off the edge of the window.
- Operator cards lead with the operator's display name.
- Modal and inherited text colours made consistent across themes.
- Generated artifacts stay consistent with the current configuration in the live
  preview.
- Expected API request cancellations no longer produce console noise.

## Security

- **Verified acquisition of the bundled OpenShift client tools.** `oc` and `oc-mirror`
  are resolved from Red Hat's official mirror at build time rather than pinned to a
  hardcoded z-stream, and each is checked against that channel's own `sha256sum.txt`
  before it is used or packaged. The resolved version, SHA256, architecture and source
  URL are recorded. Download failure, missing or unparseable checksum metadata, a
  checksum mismatch or an unsupported architecture all fail the build; there is no
  fallback to a cached binary or to unverified bytes. The container images also moved
  to Node.js 22 on UBI 9.
- Platform, BMC and proxy credentials are no longer persisted in backend state.
- Backend dependency vulnerabilities remediated, including an `undici` update and a
  refresh of audited transitive dependencies.
- An audit was performed following the June 2026 `@redhat-cloud-services` npm supply
  chain incident; dependency handling was tightened as a result.
- Repository and container ignore rules hardened so local working material cannot be
  packaged accidentally.

---

## Deprecated

- vSphere legacy placement fields are marked deprecated in favour of failure-domain
  topology paths. They continue to work; generation converts them automatically.

---

## Known limitations

- **4.22 and later are not supported** in this release. (Support for 4.22 arrives in
  v2.1 — see [v2.1.0 release notes](v2.1.0.md).)
- Exports are **not** backward-compatible with v1.x. v1.x configurations migrate forward
  automatically; there is no path back.
- Some advanced NMState host-networking options — in particular advanced bond options
  beyond mode and member interfaces — are not exposed. Bond mode and bond members are
  fully supported.
- Version identity (`v2.0.0`) describes the application code. It does not by itself
  imply enterprise distribution readiness, signed artifacts, SBOM completeness or
  compliance accreditation; those are tracked separately.

## Upgrading from v1.x

See the [full migration guide](../MIGRATION_GUIDE_v1_to_v2.md). In short:

1. Your existing saved configurations are migrated automatically when opened or
   imported — you do not need to convert anything by hand.
2. You will be asked to **confirm an OpenShift version** before you can generate. This
   is new and is required.
3. If a saved configuration names an OpenShift version outside 4.20–4.21, the app will
   stop and offer to switch you to a supported one.
4. Exported bundles from v2.0.0 cannot be read by v1.x.
