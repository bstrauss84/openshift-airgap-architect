# OpenShift Airgap Architect v2.3.0

**Version:** 2.3.0 (MINOR) · **Supported OpenShift targets:** 4.20, 4.21, 4.22 (unchanged) ·
**Status:** release candidate in preparation — **not released, not signed, not published.**

v2.3.0 adds the **Upgrade** workflow: plan a supported, disconnected update of an OpenShift 4.20, 4.21 or 4.22 cluster,
mirror exactly the releases it passes through, move them across the air gap, and follow OpenShift Update Service, CLI or
web console steps. It also makes every reset workflow-scoped and closes the N4 run-contract gap.

Build and run it the usual way:

```bash
podman compose up --build -d
# or
docker compose up --build -d
```

Before updating, save your configuration with **Tools → Export Run**. Follow [`docs/UPDATING.md`](../UPDATING.md).

## New — Upgrade workflow

Landing page → **Plan an upgrade**. Full guide: [`docs/UPGRADE_WORKFLOW.md`](../UPGRADE_WORKFLOW.md).

- **Route from the OpenShift update graph** — fetched only from `api.openshift.com` (connected side), or imported from a
  plan-package snapshot or your own OpenShift Update Service (disconnected side; Architect never fetches an address you
  type). Recommended updates only, one minor at a time, every step checked in the channel the cluster is on for it.
  Conditional updates appear only in a deliberate review with their risks and never get an executable command. The
  graph's origin, time and checksum are shown; an old or imported graph is "as of", never current. Among equally short
  routes the highest-release route is shown by convention (not a safety ranking), and the others can be chosen.
- **Stages** — every release on the route is one Upgrade-owned Mirroring profile with exactly **one pinned release per
  oc-mirror configuration**. Verified on the exact oc-mirror v2 binary: several platform channels in one configuration
  make oc-mirror add releases nobody planned, and eus-4.20 + eus-4.22 fails (the condition described in Red Hat Solution
  7087007 still applies to v2); a range with only `maxVersion` pulls 4.18/4.19 releases.
- **Runs** — each stage uses Mirroring's own preflight and runs (mirror to disk, mirror to mirror, disk to mirror,
  transfers, receive), with a post-run destination check; or run every stage as a reviewed sequence that stops at the
  first failure. Archives stay on server storage and move with the verified transfer, never through the browser.
- **Instructions** — OpenShift Update Service (recommended), CLI without OSUS (`--to-image` by release digest) and web
  console, per step, each citing the documentation of the minor it updates into. Never `--force`. Control Plane Only
  steps are withheld until their prerequisites are verified or attested.
- **Readiness** — Verified / Blocked / Warning / Attested / Not checked, from evidence only. **Check my cluster's
  readiness**: download one read-only collector script (`oc get` only; it never reads Secrets, tokens, pull secrets or
  the kubeconfig, and records no user name, cluster ID or server URLs), run it where `oc` is logged in, and upload the
  one file it writes. It covers the cluster version operator, cluster operators, machine config pools, operator
  maximum OpenShift versions, removed-API usage, administrator acknowledgements and evidence age; what it could not
  read stays "Not checked". Each check has a plain-language "How to check" guide with exact commands and the Red Hat
  documentation for its minor. The etcd backup is always your statement; Architect never asks for a restore test.
  Individual `oc get … -o json` exports remain available under Advanced.
- **Review & export** — labelled artifacts (validated, template, produced by a run) and a plan package with verified
  offline import (integrity-checked, not signed).
- **Six steps** — Route, Content, Readiness, Mirror & transfer, Update the cluster, Handoff — each answering one
  question, with a compact route strip that stays visible. Going back never loses a selection.
- **Content** — Mirroring's own operator experience per stage (Quick Picks, catalog scan, browse, constraints, Live
  catalog check, additional images), an operators-across-the-route view with categories (previously mirrored,
  installed, requested, kept) and how each is known, and "Copy stage N's operators to later stages" (each from its own
  minor's catalog). "Import previous configuration…" loads earlier ImageSetConfigurations as unverified presets with
  the file(s) each item came from (a configuration file is never evidence of what is installed or mirrored).
- **Entered once** — the mirror registry (validated: never a credential carrier) and the plan's credentials (this
  browser tab only, this plan only) serve every stage, the instructions and the templates.
- **Mirror this stage / Mirror all stages** — one reviewed confirmation that lists the jobs, where the output goes,
  the credentials used, what happens if one fails, and what will not happen (the cluster is never updated). In mirror
  to mirror, catalog tags that already exist are listed and each needs its own acknowledgement — oc-mirror replaces a
  catalog tag's content — or the plan writes catalogs under its own tag. "Open in Mirroring" offers the full workspace
  with a way straight back.
- **Progress** — each stage shows its content steps from recorded evidence (no invented percentages); whether the
  cluster was updated is your statement on "Update the cluster", never inferred from mirroring.
- **Explore older releases** — routes between any releases from 4.1 to 4.22 from real recommended edges, labelled
  "as Red Hat's update graph lists it today"; exploration only, with "Plan the supported part" where a route reaches
  4.20.
- **Client tools** — Upgrade does not package `oc`/`oc-mirror`; it names the exact versioned download and checksum
  (see N5 below). Install's existing optional bundling is unchanged.

Architect never connects to a cluster, starts an update, patches ClusterVersion or approves an InstallPlan.

## Changed — resets are scoped to their workflow

- The landing page has no global **Start Over**. Each card shows what exists and offers only its own actions; opening a
  workflow is navigation only (opening Install no longer resets Install state when no step was visited).
- **New Install…** (landing, Tools, Review, unsupported-version recovery) shows, from the server, exactly what is
  cleared, kept and stopped, and resets only the Install workflow. It never cancels a Mirroring or Upgrade job, or a
  running job whose workflow is not recorded. In-use temporary files are never removed.
- `POST /api/mirroring/start-over` (no UI caller) is retired: 410 Gone, nothing changed. Delete profiles one at a time.

## Fixed

- **Source credentials** — runs with Red Hat content are refused on the server without a Red Hat pull secret, as the
  preflight already required (disk to mirror needs none).
- **Registry references** — refused wherever they would carry a scheme, user name, password, token, query or spaces.
- A stage's operator selection could be saved into another stage after switching stages; release dropdowns could
  seem to open only from their arrow.
- **N4** — the server re-applies the preflight's destination-credential and trust rules on every run path; anonymous
  destination access is an explicit choice. Before, a crafted request could start a disk-to-mirror or mirror-to-mirror
  run without destination credentials although the preflight blocked it.
- **N7** — a memory-measurement test is robust under concurrent load.

## Known issues and limits

- Stages pin releases from `stable-<minor>`: a release that is only in the fast channel cannot be staged yet.
- Operator compatibility: a declared `olm.maxOpenShiftVersion` is read from the evidence bundle; an operator without a
  declared maximum is not proven supported, so that item stays "not checked" unless attested
  (see `docs/UPGRADE_OPERATOR_SEQUENCING.md`).
- Documentation links for update procedures await human confirmation (docs.redhat.com refuses automated checks). The
  readiness guide's book and section titles were confirmed in the openshift-docs source for 4.20, 4.21 and 4.22.
- Carried from v2.2.x: vendor CVEs in `oc`/`oc-mirror` and the Red Hat Node.js 22 base image (F21); binary-level notices
  for redistributed client tools (N5).
