# OpenShift Airgap Architect v2.1.0

**Status: not yet released.** The code is complete and has passed automated
certification; final human QA and release tagging are outstanding. Version
identity in this branch is `2.1.0-dev`.

> Upgrading from v2.0.0? Nothing you have saved needs changing. The saved-configuration
> format is unchanged, and v2.0.0 configurations open normally.
>
> Upgrading from v1.x? Read [Migration Guide: v1.x to v2.0.0](../MIGRATION_GUIDE_v1_to_v2.md)
> and the [v2.0.0 release notes](v2.0.0.md) first.

---

## What this release is about

**OpenShift 4.22 support.** v2.0.0 supported 4.20 and 4.21 and deliberately refused
anything newer. v2.1.0 adds 4.22 as a fully supported target: its own parameter
catalog, its own Field Guide, its own documentation links, and its own validation and
generation rules.

Adding a version to this application is not a configuration change. Every surface that
makes a support claim has to move together — if one of them lagged, the app would offer
you a version it could not correctly generate for. That is why the change landed as a
single coordinated update rather than piecemeal.

A second theme runs through the release: several problems only became *reachable* once
4.22 existed, and a few long-standing ones became *visible* while certifying it. Those
are fixed here too.

## Supported OpenShift versions

| Version | Status |
|---|---|
| 4.20 | Supported (baseline) |
| 4.21 | Supported |
| **4.22** | **Supported — new in this release** |
| 4.23 and later | Not supported — rejected deterministically |

Adding a version never removes one. 4.20 and 4.21 behave exactly as they did in v2.0.0.

## Added

### OpenShift 4.22 support

- Full 4.22 parameter catalogs for all twelve platform and install-method combinations.
- 4.22 Field Guide content, with documentation links that point at Red Hat's 4.22
  books.
- 4.22 documentation index covering all twelve scenarios.
- 4.22 operator catalog handling, so the operator index you mirror matches a 4.22
  cluster.
- Trust-bundle policy support for 4.22, without the "this version isn't fully reflected
  yet" caveat that would otherwise have appeared on a supported release.

The 4.22 work was built against the exact released OpenShift **4.22.16** installer,
resolved from Red Hat's stable channel and checksum-verified before use — not against a
development branch or a release candidate.

### New bare-metal setting: provisioning network gateway

OpenShift 4.22 adds one install-config parameter that Red Hat documents as a supported,
user-editable field: the **provisioning network gateway** for installer-provisioned
bare-metal clusters. It is the default gateway handed to bare-metal hosts over DHCP so
they can reach external networks during inspection and provisioning.

- Available on **bare-metal IPI at 4.22 and later** only. It does not appear at 4.20 or
  4.21, and it is not offered for Agent-based installs (Red Hat does not document it
  there).
- Only applies when the provisioning network mode is **Managed**; OpenShift ignores it
  otherwise, and so does this app.
- Validated against the rules Red Hat documents: the gateway must sit inside the
  provisioning network, outside the DHCP range, and must not collide with the cluster
  provisioning IP. Both IPv4 and IPv6 are supported, and mixing address families is
  reported explicitly rather than silently ignored.

Everything else new in 4.22 is Technology Preview or Developer Preview and is
deliberately **not** exposed. Offering a control for a feature that requires
`TechPreviewNoUpgrade` would only produce configurations OpenShift rejects.

### Safer CPU architecture handling

The app now enforces which CPU architectures are actually supported for your chosen
platform at the point configuration is generated, not only in the UI.

This matters for configurations saved by older versions. v2.0.0's architecture table
offered some combinations — vSphere on arm64, for instance — that are not supported.
Those saved configurations previously generated anyway. They are now refused with a
clear message naming the platform, install method and architecture, instead of
producing a cluster definition the product does not stand behind.

The architecture of the cluster you are building and the architecture of the installer
tooling you download remain independent choices, as they always were.

## Changed

### Operator Quick Picks now follow your OpenShift version

Quick Picks are the one-click operator presets. Several now vary by OpenShift version,
because the underlying operator catalogs do.

**OpenShift AI at 4.22** no longer requests `rhods-prometheus-operator`. That package
does not exist in Red Hat's 4.22 catalog. Previously the app asked for it anyway and
the request was silently dropped, so the preset promised four operators and mirrored
three without telling you. At 4.22 the preset is now exactly `rhods-operator`, `nfd`
and `gpu-operator-certified`. **4.20 and 4.21 are unchanged** — the package still
exists there.

No replacement was substituted. Red Hat's OpenShift AI operator does not depend on that
package, ships no Prometheus images, and Red Hat's own disconnected-install guide does
not mention it.

**ODF presets** gained the packages Red Hat's 4.22 documentation adds —
`ocs-tls-profiles`, and `odr-volsync-plugin-operator` for disaster-recovery
deployments.

### Service Mesh preset no longer requests the Jaeger operator

`jaeger-product` was removed from the Service Mesh preset. Red Hat removed the Jaeger
operator from its operator catalog, and support for it ended in November 2025 — before
any OpenShift version this app supports. The preset had been requesting a package that
no catalog carried, so it quietly delivered two operators instead of three.

The preset is now `servicemeshoperator` and `kiali-ossm`.

**Nothing was substituted in its place.** Current Red Hat Service Mesh handles
distributed tracing through separate Tempo and OpenTelemetry operators, and Red Hat
documents those as prerequisites of an *optional* tracing integration rather than part
of Service Mesh itself. Bundling them into the base preset would add a capability
rather than fix a stale reference. Whether to offer a separate optional tracing preset
is an open question.

### Switching OpenShift versions is safer

Changing version now consistently re-applies the new version everywhere: parameter
catalogs, documentation, architecture options, operator state and the generated
preview. Settings that exist only in a newer release are kept in your configuration but
are neither shown nor written out while you are targeting an older one — so switching
away and back does not lose your work, and never leaks a setting into a file that
cannot accept it.

### Clearer errors for inconsistent configurations

If a configuration's version fields contradict each other, the app now reports it as a
configuration problem with a readable message, rather than surfacing a generic server
error. It still refuses to generate anything — picking one of the conflicting versions
silently would be worse — but it no longer looks like a crash.

## Fixed

- **Corrected Day-1 SR-IOV host network generation.** The virtual-function count is now
  written under the documented `ethernet.sr-iov` structure. Previously it was placed at
  the wrong level, which OpenShift rejects — and because that rejection applies to the
  whole host's network configuration, an Agent-based install would fail rather than just
  losing the SR-IOV setting. If you have a saved configuration with SR-IOV enabled, it
  will now generate correctly with no changes on your part. This affected v2.0.0 too.
- A stale provisioning-network-gateway value no longer blocks generation after you
  switch the provisioning network to Unmanaged or Disabled. OpenShift ignores the field
  in those modes, the UI hides it, and it would have been impossible to correct without
  switching back. Validation now applies only where the field actually applies.
- Operator presets no longer silently drop packages that a catalog does not carry; every
  package a preset names now resolves. (See the OpenShift AI and Service Mesh changes
  above.)
- The end-to-end test harness can no longer certify the wrong application build — see
  below.

## Security

- Credential handling, export sanitisation and the credential-canary checks that
  protect them were re-certified against all three supported versions.
- Production dependency audits remain clean for both backend and frontend.
- Error responses for invalid configurations were verified to contain no credentials,
  no server file paths and no stack traces.

---

## Testing and certification

- Real generated output was certified for **all twelve** platform and install-method
  combinations at 4.22 — not just checked against the catalog.
- The platform × install-method × architecture matrix grew from 96 to 144 verified
  combinations, with every supported combination checked against real generated YAML
  and every unsupported one proven to be refused.
- All six version-transition directions between 4.20, 4.21 and 4.22 are covered.
- Import, export, bundle contents and bundle manifests are certified at all three
  versions.
- The end-to-end harness now **verifies which build it is testing** before running.
  During certification it was discovered that the suite had been running against a
  stale pre-release container rather than the build under test — producing confident
  results about the wrong code. The harness now checks the application version, the set
  of supported OpenShift versions and the source revision, and refuses to run on a
  mismatch.

## Known limitations

- **Human QA is not complete.** Browser-level and manual acceptance testing is
  outstanding; this release should not be considered final until that is done.
- **Host networking supports a documented subset of NMState, not all of it.** For
  Agent-based installs OAA generates interface, IPv4/IPv6, bond, VLAN, VRF, route and
  DNS configuration. Anything outside that subset must still be written by hand. The
  supported set is identical on 4.20, 4.21 and 4.22.
- Bare-metal **IPI** host networking is more limited than Agent-based: a single ethernet
  interface with an IPv4 address, DNS and a default route. Bond, VLAN, IPv6 and MTU are
  available for Agent-based installs only.
- Advanced NMState bond options beyond bond **mode** and bond **members** — such as
  `xmit_hash_policy`, `lacp_rate`, `updelay` and `downdelay` — are still not
  configurable. This is unchanged from v2.0.0 and applies equally to 4.20, 4.21 and
  4.22. OAA also offers two of the three bond modes OpenShift supports
  (`active-backup` and `802.3ad`); `balance-xor` is not currently offered.
- The Service Mesh preset no longer includes distributed tracing. If you need tracing,
  add the Tempo and OpenTelemetry operators yourself.
- Two documentation gaps carried over from v2.0.0 remain open: some Field Guide
  documentation links for 4.20 and 4.21 point at book paths that have since moved, and
  the Azure Government UPI scenario has no documentation-index entry at 4.20 or 4.21.
  Neither affects generated configuration, and neither affects 4.22.
