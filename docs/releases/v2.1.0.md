# OpenShift Airgap Architect v2.1.0

**Status: not yet released.** The automated test suites (backend, frontend,
tooling, release-certification) pass; the release itself has not been cut.

**How v2.1 is delivered.** This release is distributed as **source plus a
Docker/Podman Compose deployment** — clone or download the source, build the
two images locally, and run `docker compose up --build`. There are no prebuilt
images to pull. [`docs/UPDATING.md`](../UPDATING.md) covers upgrading an
existing installation.

- **The API is authenticated, and the local Compose deployment is deliberately
  not.** The backend enforces identity, an origin allowlist and CSRF defence,
  and refuses to start in an unsafe configuration — including refusing a
  non-loopback bind when authentication is disabled. Compose runs it
  unauthenticated and bound to loopback, which is the supported single-user
  developer configuration; **do not publish those ports on a network.**

- **Kubernetes and OpenShift manifests are included, and are outside the v2.1
  delivery scope.** `manifests/` carries a full authenticated topology:
  built-in OpenShift OAuth (`oauth-proxy`) in front of a single Route, `/api`
  proxied same-origin, no backend Route at all, a NetworkPolicy, a shared
  secret the backend requires, and `restricted-v2`-compatible pod security.
  Read [`manifests/README.md`](../../manifests/README.md) before applying it:
  it carries the procedure, the two secrets you must create yourself, and the
  post-deploy checks — including the NetworkPolicy check, which is the one not
  to skip, because a network plugin that does not enforce policy accepts the
  object and restricts nothing. Clusters configured for **direct external OIDC
  are not supported** by this mode; the backend refuses to start rather than
  failing at login.

  **Five defects in that implementation were found and closed on 2026-10-19**,
  before release: the backend bound every interface while its startup guard
  checked a `BIND_ADDRESS` nothing consumed; the overlay shipped the proxy
  `Secret` with empty values, so the documented second `oc apply -k` would
  have blanked the operator's real keys; nginx served the pre-authentication
  port on the pod IP while forwarding caller identity and attaching the
  backend's shared secret, which made NetworkPolicy the only thing standing
  between any namespace pod and an authenticated session; the Route carried a
  `service.beta.openshift.io/inject-cabundle` annotation that does nothing on
  a Route; and the nginx resolver named a DNS Service that does not exist on
  OpenShift. Each has a focused regression test, including two that make real
  network connections rather than asserting on configuration strings. See
  `docs/releases/evidence/REQUIREMENT_LEDGER_AUTH_CORRECTIONS_20261019.md`.
- **The container images carry unresolved vulnerabilities, and the scan says so.**
  A candidate-bound scan on 2026-10-20 reports **backend 1 critical / 110 high**
  and **frontend 0 critical / 48 high**. The `image-vulnerabilities` axis
  **FAILs** on that, and the failure is published rather than waived.

  Of the 159 critical/high findings, **56 are inside Red Hat's own `oc` and
  `oc-mirror` binaries** — including the only critical — which this project ships
  verbatim and cannot patch without forking an artifact Red Hat supports. Both are
  already at 4.22.18, the newest version Red Hat's channels publish. The remaining
  **103 are UBI base-image packages, and none of them has a fixed package
  available**: no newer base image clears them, because Red Hat has not published
  one. Scan counts move with the vulnerability database; the raw scanner output is
  attached to the release, and it, not this paragraph, is the evidence. See
  [SBOM and provenance](../security/SBOM_AND_PROVENANCE.md).

Release tagging is the remaining step. Until the version below is stamped, the
version identity in this branch is a development one.

> **Upgrading from v2.0.0?** The saved-configuration **format** is unchanged — both
> releases use schema v3 — so v2.0.0 configurations open without conversion. Two
> things can still require action from you:
>
> - **A configuration using an unsupported platform/architecture combination is now
>   refused at generation.** v2.0.0's architecture table offered combinations the
>   product does not support, such as vSphere on arm64, and generated them anyway.
>   Those configurations now fail with a message naming the platform, install method
>   and architecture. See [Safer CPU architecture handling](#safer-cpu-architecture-handling).
> - **Credentials must be re-entered after Tools → Import Run.** A re-imported JSON
>   Run no longer carries credentials.
>
> An earlier revision of this note said "Nothing you have saved needs changing".
> That overstated it on both counts above, and contradicted this document's own
> architecture-enforcement section. Note also that the automated suites certify the
> v1.x → v3 migration boundary; there is **no fixture that specifically certifies
> opening a v2.0.0-saved configuration under v2.1**. The format is unchanged, so no
> migration step runs — but that is an argument from the schema, not a tested result.
>
> Upgrading from v1.x? Read [Migration Guide: v1.x to v2.0.0](../MIGRATION_GUIDE_v1_to_v2.md)
> and the [v2.0.0 release notes](v2.0.0.md) first.

## What this release is about

**OpenShift 4.22 support.** v2.0.0 supported 4.20 and 4.21 and deliberately refused
anything newer. v2.1.0 adds 4.22 as a fully supported target: its own parameter
catalog, its own Field Guide, its own documentation links, and its own validation and
generation rules.

Adding a version to this application is not a configuration change. Every surface that
makes a support claim has to move together — if one of them lagged, the app would offer
you a version it could not correctly generate for. That is why the change landed as a
single coordinated update rather than piecemeal.

A second theme runs through the release: several problems only became *reachable* once
4.22 existed, and a few long-standing ones became *visible* while certifying it. Those
are fixed here too.

## Supported OpenShift versions

| Version | Status |
|---|---|

| **4.22** | **Supported — new in this release** |

## Added

### OpenShift 4.22 support

- Full 4.22 parameter catalogs for all twelve platform and install-method combinations.
- 4.22 Field Guide content, with documentation links that point at Red Hat's 4.22
  books.
- 4.22 documentation index covering all twelve scenarios.
- 4.22 operator catalog handling, so the operator index you mirror matches a 4.22
  cluster.
- Trust-bundle policy support for 4.22, without the "this version isn't fully reflected
  yet" caveat that would otherwise have appeared on a supported release.

The 4.22 work was built against the exact released OpenShift **4.22.16** installer,
resolved from Red Hat's stable channel and checksum-verified before use — not against a
development branch or a release candidate.

### New bare-metal setting: provisioning network gateway

OpenShift 4.22 adds one install-config parameter that Red Hat documents as a supported,
user-editable field: the **provisioning network gateway** for installer-provisioned
bare-metal clusters. It is the default gateway handed to bare-metal hosts over DHCP so
they can reach external networks during inspection and provisioning.

- Available on **bare-metal IPI at 4.22 and later** only. It does not appear at 4.20 or
  4.21, and it is not offered for Agent-based installs (Red Hat does not document it
  there).
- Only applies when the provisioning network mode is **Managed**; OpenShift ignores it
  otherwise, and so does this app.
- Validated against the rules Red Hat documents: the gateway must sit inside the
  provisioning network, outside the DHCP range, and must not collide with the cluster
  provisioning IP. Both IPv4 and IPv6 are supported, and mixing address families is
  reported explicitly rather than silently ignored.

Everything else new in 4.22 is Technology Preview or Developer Preview and is
deliberately **not** exposed. Offering a control for a feature that requires
`TechPreviewNoUpgrade` would only produce configurations OpenShift rejects.

### Safer CPU architecture handling

The app now enforces which CPU architectures are actually supported for your chosen
platform at the point configuration is generated, not only in the UI.

This matters for configurations saved by older versions. v2.0.0's architecture table
offered some combinations — vSphere on arm64, for instance — that are not supported.
Those saved configurations previously generated anyway. They are now refused with a
clear message naming the platform, install method and architecture, instead of
producing a cluster definition the product does not stand behind.

The architecture of the cluster you are building and the architecture of the installer
tooling you download remain independent choices, as they always were.

## Changed

### Operator Quick Picks now follow your OpenShift version

Quick Picks are the one-click operator presets. Several now vary by OpenShift version,
because the underlying operator catalogs do.

**OpenShift AI at 4.22** no longer requests `rhods-prometheus-operator`. That package
does not exist in Red Hat's 4.22 catalog. Previously the app asked for it anyway and
the request was silently dropped, so the preset promised four operators and mirrored
three without telling you. At 4.22 the preset is now exactly `rhods-operator`, `nfd`
and `gpu-operator-certified`. **4.20 and 4.21 are unchanged** — the package still
exists there.

No replacement was substituted. Red Hat's OpenShift AI operator does not depend on that
package, ships no Prometheus images, and Red Hat's own disconnected-install guide does
not mention it.

**ODF presets** gained the packages Red Hat's 4.22 documentation adds —
`ocs-tls-profiles`, and `odr-volsync-plugin-operator` for disaster-recovery
deployments.

### Service Mesh preset no longer requests the Jaeger operator

`jaeger-product` was removed from the Service Mesh preset. Red Hat removed the Jaeger
operator from its operator catalog, and support for it ended in November 2025 — before
any OpenShift version this app supports. The preset had been requesting a package that
no catalog carried, so it quietly delivered two operators instead of three.

The preset is now `servicemeshoperator` and `kiali-ossm`.

**Nothing was substituted in its place.** Current Red Hat Service Mesh handles
distributed tracing through separate Tempo and OpenTelemetry operators, and Red Hat
documents those as prerequisites of an *optional* tracing integration rather than part
of Service Mesh itself. Bundling them into the base preset would add a capability
rather than fix a stale reference. Whether to offer a separate optional tracing preset
is an open question.

### Switching OpenShift versions is safer

Changing version now consistently re-applies the new version everywhere: parameter
catalogs, documentation, architecture options, operator state and the generated
preview. Settings that exist only in a newer release are kept in your configuration but
are neither shown nor written out while you are targeting an older one — so switching
away and back does not lose your work, and never leaks a setting into a file that
cannot accept it.

### Clearer errors for inconsistent configurations

If a configuration's version fields contradict each other, the app now reports it as a
configuration problem with a readable message, rather than surfacing a generic server
error. It still refuses to generate anything — picking one of the conflicting versions
silently would be worse — but it no longer looks like a crash.

## Fixed

- **Corrected Day-1 SR-IOV host network generation.** The virtual-function count is now
  written under the documented `ethernet.sr-iov` structure. Previously it was placed at
  the wrong level, which OpenShift rejects — and because that rejection applies to the
  whole host's network configuration, an Agent-based install would fail rather than just
  losing the SR-IOV setting. If you have a saved configuration with SR-IOV enabled, it
  will now generate correctly with no changes on your part. This affected v2.0.0 too.
- A stale provisioning-network-gateway value no longer blocks generation after you
  switch the provisioning network to Unmanaged or Disabled. OpenShift ignores the field
  in those modes, the UI hides it, and it would have been impossible to correct without
  switching back. Validation now applies only where the field actually applies.
- Operator presets no longer silently drop packages that a catalog does not carry; every
  package a preset names now resolves. (See the OpenShift AI and Service Mesh changes
  above.)
- The end-to-end test harness can no longer certify the wrong application build — see
  below.

### Upgrade safety

- **Tools → Export Run no longer exports a stale snapshot.** Export downloads the
  server's copy of the run, but edits reached the server through a 600 ms debounce, so
  exporting immediately after an edit produced a file that silently predated it —
  precisely the file you would restore from after updating. Export now flushes any
  pending save first, and a save failure surfaces and **cancels** the export instead of
  being swallowed and emitting a backup that does not match what is on screen.
- **The update banner no longer reports an update that does not exist.** It fired
  whenever the configured branch head differed from the running build. At the time,
  no GitHub Release had been published and `APP_BRANCH` defaulted to `main`, which
  still pointed at the v1.7.1 commit — so a running v2.1 build was being told to
  update to something five months *older* than itself. The check now reports a
  distinct state,
  and only a verified published release raises the urgent banner. No trusted
  release-identity source exists yet, so that state is currently unreachable by design.
- **The urgent banner now carries backup guidance.** It names Tools → Export Run before
  updating and Tools → Import Run afterwards, states that credentials are excluded and
  must be re-entered, and distinguishes the **run JSON** from the generated **bundle
  ZIP**. It previously pointed at Tools → About, which contained no update steps.

### Deployment, container and process lifecycle

These were found while certifying the release. They are listed because they change
behaviour operators can observe, not merely build internals.

- **The shipped container images could not start under Kubernetes or OpenShift.** The
  backend entrypoint called `runuser` unconditionally, which a non-root caller cannot
  use — so with the project's own `manifests/base/` securityContext (`runAsNonRoot`,
  `capabilities: drop ALL`) the container exited immediately. Startup now detects
  whether it has root: with root it chowns the data directory and drops privileges as
  before; without root it skips straight to running the server, and reports an
  unwritable data directory in terms of the `fsGroup` an operator can actually set,
  rather than failing later as an opaque SQLite error.
- **Shutdown no longer leaves credentials on disk.** Cleanup for a child process —
  marking its job finished, unlinking its registry auth file, removing its `registries.d`
  directory — lived in that child's close handler, and the process exited before any of
  it ran. Pull secrets could be left behind on the data volume. Shutdown now performs
  that cleanup synchronously, and an interrupted job is recorded as `cancelled` rather
  than being misdiagnosed as `failed` on the next start.
- **High-side runtime-package staging directories are now reliably removed**, and a
  removal that fails is reported rather than assumed to have worked.
- **An export that could not include everything you asked for now fails instead of
  being delivered incomplete.** Exported bundles record the deliverables explicitly
  requested, so a requested tool whose download failed ends the export rather than
  producing an archive that silently lacks it — something you would otherwise discover
  on the far side of the air gap, where the mirror is unreachable by definition.
  Documented degraded modes, such as the high-side runtime package being absent when no
  container engine is present, are deliberately not treated as failures. AWS installer
  versions are additionally guarded.
- Both shipped images now carry build-provenance labels binding them to the source
  revision they were built from. Previously the only revision label present was
  inherited from the Red Hat base image and described Red Hat's build, not this one.

## Security

- Credential handling, export sanitisation and the credential-canary checks that
  protect them were re-certified against all three supported versions.
- Production dependency audits remain clean for both backend and frontend.
- Error responses for invalid configurations were verified to contain no credentials,
  no server file paths and no stack traces.
- **The backend image ships a much smaller attack surface.** It now builds on Red Hat's
  Node.js 22 S2I image but *ships* on `ubi9/nodejs-22-minimal`, which carries no C/C++
  toolchain. The previous single-stage image inherited `kernel-headers` from its base,
  which alone accounted for 141 of the backend's 200 OS-package HIGH findings. Red
  Hat's `nodejs-nodemon` — a development file-watcher this container never invokes — is
  also removed. These are base-image and packaging changes; they do not alter
  application behaviour.

> **Vulnerability scanning is not a clean result.** Image scanning runs and produces
> real findings, and the most recent full run's `image-vulnerabilities` axis verdict is
> **FAIL**. That scan is also bound to a stale candidate. No finding has been triaged
> into an accepted / false-positive / will-not-fix disposition. See
> [SBOM and provenance](../security/SBOM_AND_PROVENANCE.md) for exactly what is
> generated, what is not, and why none of it is published yet.

### Removed endpoints

- **`POST /api/bundle.import`** now returns `410 ENDPOINT_WITHDRAWN`. It was an
  unauthenticated decompression denial of service — the only ingress exempt from the
  10 MB JSON cap, it accepted 512 MiB and inflated every entry synchronously, costing
  roughly a gigabyte of memory and seconds of blocked event loop per request and
  starving the health probe. No UI, CLI or documented workflow used it, so there is no
  user-visible loss. The validator itself is unchanged; re-exposing it is tracked as
  DOC-127.
- **`GET /api/secrets/rh-pull-secret/content`** now returns `410 ENDPOINT_WITHDRAWN`.
  It returned the full mounted Red Hat pull secret to any caller.

### Changed behaviour you may notice

- The Blueprint pull-secret field is **no longer pre-populated** from a backend-mounted
  pull secret; the credential is never sent to the browser. An informational badge
  reports that a mounted secret is present. Mirror operations still authenticate with it
  server-side via the "Use mounted Red Hat pull secret" option. Manual paste/upload, the
  "Retain pull secret for use on subsequent pages" checkbox, carry-forward to Identity &
  Access, and generated install-config `pullSecret:` are all unchanged.
- **Bundle export: mirror output must live under the application data directory.** The
  export boundary is now enforced against the real filesystem — paths are canonicalised
  with `realpath`, symbolic links anywhere in the tree are refused, and files whose names
  look like credential material are refused. `/tmp` is no longer exportable. An unsafe
  path now fails the download with a `400` naming the offending entry, instead of
  producing a ZIP that silently omits the directory. If you pointed mirror output at
  `/tmp`, move it under the data directory; the product default already complies.
- **A re-imported JSON Run no longer carries credentials.** `Tools → Import Run` now
  applies the same credential stripping as ordinary state persistence, so SSH private
  keys, platform and BMC passwords, and any userinfo embedded in a proxy URL are removed
  before the run is stored. **Re-enter credentials after importing.** Non-sensitive
  configuration, proxy endpoints and v1.x/v2.x migration are unaffected. This is the
  Export Run → upgrade → Import Run path, so it matters most when upgrading.
- oc-mirror run request bodies are credential-stripped before being stored in job
  metadata, so `GET /api/jobs` no longer returns pull secrets.

> **Resolved in this release, pending live verification.** The backend now
> enforces identity on every route except the kubelet probes, replaces
> wildcard CORS with an origin allowlist, and refuses state-changing requests
> that carry a foreign `Origin`. The OpenShift overlay authenticates one Route
> with built-in OpenShift OAuth and no longer publishes the backend at all.
>
> Two things to know, stated rather than buried:
>
> - **The boundary is covered by negative tests, and the cluster topology is
>   outside v2.1's delivery scope.** The backend's refusals are proven by
>   tests that forge identity headers, call the Service directly, submit
>   cross-site form POSTs and attempt cross-origin reads; the overlay's shape
>   is pinned by rendering guards. Applying that overlay is a separate
>   exercise with its own procedure and post-deploy checks in
>   [`manifests/README.md`](../../manifests/README.md).
> - **Local Compose remains unauthenticated by design**, and the backend now
>   refuses to start in that mode unless it is bound to loopback. It is a
>   single-user developer configuration; do not expose it on a network.

## Testing and certification

- Real generated output was certified for **all twelve** platform and install-method
  combinations at 4.22 — not just checked against the catalog.
- The platform × install-method × architecture matrix grew from 96 to 144 verified
  combinations, with every supported combination checked against real generated YAML
  and every unsupported one proven to be refused.
- All six version-transition directions between 4.20, 4.21 and 4.22 are covered.
- Import, export, bundle contents and bundle manifests are certified at all three
  versions.
- The end-to-end harness now **verifies which build it is testing** before running.
  During certification it was discovered that the suite had been running against a
  stale pre-release container rather than the build under test — producing confident
  results about the wrong code. The harness now checks the application version, the set
  of supported OpenShift versions and the source revision, and refuses to run on a
  mismatch.

## Known limitations

- **Human QA is not complete.** Browser-level and manual acceptance testing is
  outstanding; this release should not be considered final until that is done.
- **Host networking supports a documented subset of NMState, not all of it.** For
  Agent-based installs OAA generates interface, IPv4/IPv6, bond, VLAN, VRF, route and
  DNS configuration. Anything outside that subset must still be written by hand. The
  supported set is identical on 4.20, 4.21 and 4.22.
- Bare-metal **IPI** host networking is more limited than Agent-based: a single ethernet
  interface with an IPv4 address, DNS and a default route. Bond, VLAN, IPv6 and MTU are
  available for Agent-based installs only.
- Advanced NMState bond options beyond bond **mode** and bond **members** — such as
  `xmit_hash_policy`, `lacp_rate`, `updelay` and `downdelay` — are still not
  configurable. This is unchanged from v2.0.0 and applies equally to 4.20, 4.21 and
  4.22. OAA also offers two of the three bond modes OpenShift supports
  (`active-backup` and `802.3ad`); `balance-xor` is not currently offered.
- The Service Mesh preset no longer includes distributed tracing. If you need tracing,
  add the Tempo and OpenTelemetry operators yourself.
- Two documentation gaps carried over from v2.0.0 remain open: some Field Guide
  documentation links for 4.20 and 4.21 point at book paths that have since moved, and
  the Azure Government UPI scenario has no documentation-index entry at 4.20 or 4.21.
  Neither affects generated configuration, and neither affects 4.22.
